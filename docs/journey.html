The journey so far

Sherpa-B has one task at this point — “Build the first version of your app.” The stages below are the participant’s own decomposition of it. Each carries the exact decision prompts and the reasoning behind them — the reversals included.

00

Orientation — set the target, not the vision

weekend 1

KnowledgeOps Phase 1: define a problem worth solving. Orientation also fixes the autonomy level — how much of each loop the AI runs vs. the human — as a deliberate choice, not a default. The Block’s risk is trajectory: am I pointed at something real and buildable?

Autonomy ladder — how much the human is in the loop
L1Assistant — the human directs each step; the AI does single, specified tasks.
L2Collaborator — the AI drafts a whole pass (a plan, a design, an implementation); the human reviews and approves or redirects each pass.
L3Agent — the AI takes an objective and runs multi-step work, checking in at milestones; the human reviews outcomes, not every step. L4Operator — the AI runs continuously; the human sets policy and audits.

L1 — AssistantL2 — CollaboratorL3 — Agent
Chose L2 — explicitly a starting point, to level up from as trust in the agent grows.
Claude asked · OrientationWhat milestone shape are you going for?
A polished product twin firstOne feature end-to-end
Chose “one feature end-to-end” — a single real H5P feature change, demoed as if live, building only the context that feature needs.

PM · orientation reflection, in their words

“I started thinking in terms of ‘build a digital twin of the product’ and narrowed it to ‘produce one real H5P feature change and demo it as if live.’ Autonomy also became a conscious choice rather than a default — starting at L2, with the intent to level up as I learn what the agent can be trusted with.”

Where it landed Project defined; autonomy L2; milestone = one feature, end-to-end. Cadence: weekends only.

01

Reframe: from “digital twin” to a real feature

weekend 1 & 3

The original idea was an agent that builds a “digital twin” of any SaaS product so PMs can prototype changes without engineering. That narrowed twice: first to H5P during orientation, then — weeks in — to a single feature, with the twin idea dropped entirely.

KnowledgeOps · Phase 1  ·  Block risk · trajectory

PM · weeks in

“Make this project about H5P Smart Import, and not the H5P Twin we were thinking about. Let’s dedicate this to Smart Import. The initial walkthrough was just to make you understand the existing flow.”

Spec, profile and prototype re-titled. Goal stated plainly: reduce time-to-value, lift W1→W2 retention. The prototype is re-framed as a means to test and demo the workflow — not a deliverable in itself.

Why the pivot mattered

“Build a twin of any product” is unfalsifiable and can’t be demoed in three weekends. “Fix Smart Import’s ~20% retention” is a testable bet with a number attached. A vision you can’t demo by the sprint is the backdrop, not the milestone.

Where it landed Project = rework H5P Smart Import’s educator workflow. North star = time-to-value and W1→W2 retention.

02

Learn the existing product

weekend 1

Not a KnowledgeOps phase — the PM’s own reconnaissance. Establish what Smart Import actually does today, step by step, and where it loses people, before proposing anything.

Claude askedHow should I get access to Smart Import to learn it?
You paste me the help docsI drive — browser automation on your logged-in session
Chose “I drive” — Claude clicked through Smart Import in the PM’s own browser session. No engineering access, no sandbox.

PM · during the run

“Run it yourself — in upload, use paste text and paste some 500-word text on the topic there.” … “Have you now understood the workflow happy path?” “No, this was just to teach you about the workflow. Now suggest UX improvements on the workflow.”

Mapped the real path: Configure → Select → Generate → each activity dumped into one folder → open every item in the full editor to fix it. Catalogued the friction at each step.

The read

The cliff isn’t generation quality — it’s no preview before spend, N separate editors to clean up, and a flat folder dump. That’s a trust-and-cleanup-cost problem, not an activation one — and compounding features (memory, discoverability) can’t fix an 80% drop, only serve the people who already came back.

Architect note To demo workflow changes credibly you have to reproduce the product’s real I/O — a source in, valid H5P content.json rendered in the actual player — not a mockup. That one decision shaped the whole build.

Where it landed A shared understanding of the current flow and its friction, written into the spec as the thing the rework has to beat.

Designing the four parts of the workflow

03

Part 1 — Express intent

weekend 1–2

How the educator says what they want, from what source. Today: one collapsed, optional “Customization” box, usually skipped.

PM

“Think of custom prompt — it could be a generic prompt, or a design brief (a guided form with questions on learning goal, audience, difficulty…), or predesigned prompt options they can click, or a button to make their typed prompt better based on prompt-engineering best practice.”

Became: a prompt XOR a guided brief (mutually exclusive — a free prompt and structured fields can contradict, and it’s ambiguous which wins), plus preset prompts, an “improve” action, and a save-and-reuse library.

PM · on the source read-back

“Make it in a way that doesn’t reduce TTV for creation of content. It should just tell authors the strengths and drawbacks of the source material, not discourage them from using it — that’s their choice.”

The read-back became strictly advisory and non-blocking: it describes the material, it never gates or nudges away from generating. It fills in behind the “Choose activities” button, which is live the moment a source exists.

PM · on “improve this prompt”

“It adds a guideline to the user — I want it to create an improved prompt based on what the user typed, following better prompt-engineering guidelines from whatever info is in the rough prompt.”

“Improve” became a rewrite of the user’s text — imperative, specific — that only fills in audience / focus / count / difficulty where the rough text already implies them. It never invents intent.

PM · a question that closed a door

“Do the learning objectives in the source read-back align well with the predesigned prompts, or should we allow one or the other, not both?”

They’re different things — objectives are content targets read off the source; a preset prompt is framing. Rather than risk them fighting, source-derived draft objectives were parked. Also rejected outright: “suggest a full prompt from the source” — the prompt exists to carry intent (audience, formative vs. summative, the sub-topic students struggle with), none of which is in the learning material.

Where it landed Prompt-or-brief authoring · presets · “improve” · a reusable template library · an advisory source read-back · verbatim question extraction. The blank box is the problem, not the freedom.

04

Part 2 — Activity fit

weekend 2

Which H5P activity types get generated, and how many. Today: a wall of blind checkboxes with no fit-to-source signal, no counts, no coverage view.

PM

“Recommended activities are pre-checked from your source and intent. Is there a rule or logic here — how do you determine? Think more about what the right way of recommending content is, and how inputs like source material and prompt impact it.”

Two inputs doing two different jobs. The source answers “can a good activity of this type even be built from this raw material?” — feasibility, which requires reading the text, so it’s an LLM call folded into the read-back. The intent answers “which feasible types serve the teacher’s goal?” — desirability, which is pure rules and re-ranks instantly when emphasis or volume changes. Source is never overridden by an intent that wants something infeasible.

PM

“How will you decide the number of activities, and what if the user mentions a specific number in the prompt?”

Default 2 (one recall + one understanding); 1 for a short or single-topic source; 3 only when the source is long and multi-section and the intent signals breadth. If the prompt names a number, that wins — but it’s still bounded by what the source supports: ask for 10, get 7 good ones, and say so at the gate. Never silently pad, never silently ignore.

PM · scoping the output

“Make sure this logic results in just recommended content types. The rule engine should be documented in the spec, and we will refine it over time.”

The engine’s only output is the pre-checked set + a count + a one-line reason per type. It doesn’t generate, gate, or pick destinations. Every threshold is written down as a dial — v1 to be tuned from usage.

Where it landed A recommendation engine v1: feasibility gate (LLM, from source) + desirability rank (rules, from intent) + count logic + item counts + reasons, all overridable.

05

Part 3 — Review & refine (the core)

weekend 2

Seeing what the AI produced and deciding whether to trust it — today a black-box wait, then N content items and the full editor. This is the stage that retires the trust risk and is the retention fix.

PM · after seeing the first review UI

“The 3 options are regenerate, edit, approve. In complex types like a quiz, I’m not sure we should allow it at sub-content level. It wasn’t possible to navigate the content within a single quiz without answering it — that seemed odd. And the truth signal was the same for all questions in the quiz?”

Three fixes: a Review view that lays every question out to scan without answering; per-question trust signals (the source sentence, an answer-key note, a confidence level — not one signal for the whole activity); and a clear split — item level is edit-text-only, AI refinement is activity level (regenerating one question in isolation breaks coherence with the rest).

PM · reframing the job

“Think about the approve / discard / edit workflow better — what will an educator want to do here as a job if they’re not happy with the content? Even for discard, we must find out why, just like for regenerate.”  …  “Make it simple for MVP.”

Landed on three bounded actions, each logged: Refine (same type, one steer from a closed list) · Remix (rebuild as a different type, keeping the concepts) · Discard (with a reason). Approve is the default, not a click. A soft cap of 3 refines, then the tool points at Remix or Discard — because by then the source×type pairing is the likely problem.

PM · “what about language / tone / difficulty?”

“What about refinement like — make this content in this language, adjust tone, change difficulty?”

Those are the Refine steers — not a separate mechanism. One vocabulary of bounded steers, used the same way here and in any later post-creation refinement.

Claude askedWhat should “Remix” do at the review stage?
Change activity type — reuse the concepts, rebuild in a new formatAlternative take — branch, keep bothRecombine items across activities
Chose “change activity type” — the positive path for “wrong format”, replacing a discard-and-re-pick detour.

PM · the CPO’s challenge

“The CPO says evals aren’t important — the quality of content produced from source is good enough, in his eyes.”

The approval gate exists anyway; make it a measurement stream. Every Refine / Remix / Discard / edit writes a review_event with full context, and the whole import is persisted as an ImportRecord. “Quality is good enough” then becomes a number — approve-without-edit rate — not an opinion.

Architect note A “chat agent inside each activity” for later editing sounds like a new system. It’s the same regenerate engine and the same steer library behind a different shell. Naming that boundary stopped a small feature from turning into a big one.

Where it landed A Review & Approve step behind a “Create N” gate · live H5P preview per item · per-question trust signals · bounded Refine / Remix / Discard · approve-by-default · a labelled review_event stream.

06

Part 4 — Find & reuse it later

weekend 2–3

Where the created content lives and how it’s traced back. Today: a flat dump into a “Smart Import” folder, with a title prefix as the only clue to which import made what.

PM · raising the fourth part

“Add a fourth stage about discoverability. The content, once created, goes into one folder called ‘smart imports’, and there’s no easy way to figure out which content was created from a given Smart Import session.”  …  “There’s one Smart Import with all content across all imports. Do we need both those views, or can it be merged?”

The import is an event — an immutable receipt (source, intent, decisions). The content items are living objects that belong in the library. Keep two indexes — “what did I import?” and “what content do I have?” — joined by a two-way link, not a folder. Merge the folders (both of them), not the views. Don’t file the goods in a drawer named after the receipt.

PM

“How do we store info related to an import though — the occasional lookup?”

A persisted ImportRecord: source snapshot, intent, engine/model, outcome counts, the per-item decision trail, and the kept items. Reached from any content item’s from: tag; survives a reload and “start another import”.

Claude askedHow should a new import be named by default?
Timestamp, editableSequence + timestampTimestamp only, fixed
Chose “timestamp, editable” — identity shouldn’t be tied to what the import happened to be about.
Reversed a turn later: “I disagree on naming, keep it same as the topic.” — topic + date it stayed. A small reminder that the person testing it has the last word on what feels right.
Claude askedHow much of the lookup surface to build now?
Record + a browsable Smart Imports listRecord + details only
Chose “record + details only” — persist the receipt, reach it from the from: tag; the standalone list is a later phase.

Where it landed Content lands in the library (no dedicated folder) · a from: provenance tag + filter · a persisted ImportRecord receipt. Naming: topic + date.

Building & instrumenting the prototype

07

Build the prototype

weekend 1–2

A first working version — enough to run the reworked flow on a real source and see real output. Mostly execution rather than decision points; the calls that mattered were architectural.

Block risk · engineering  ·  KnowledgeOps · Phase 5 (early)

The three calls that shaped the build
Real playerRender generated content.json in the actual H5P standalone player, with libraries pulled from H5P’s content-type hub — so the demo survives “would you actually use this?” Model-or-mockUse an LLM when an API key is present; a deterministic mock otherwise. The workflow is the product; the model is a swappable dependency. Per-type callsOne LLM call per content type, each with a format-only structure reference (a real example content.json, no topic content). A single combined call had been returning the wrong type for some activities.

Where it landed A Next.js app: generate-from-source engine, the 13-activity catalogue, the wizard flow, and real H5P rendering. Content grounded strictly in the provided source.

08

Instrument it — the eval stream & measurement

weekend 3

The Block that retires the trust risk (Phase 2: Evaluation Design) asks for an evaluation dataset. This stage lays the pipe while building the feature.

PM

“How do we measure adoption, usage and retention now? How do we measure time-to-value and the success of this workflow?”

A funnel with one event per stage: import_started → generate_completed → item_previewed → create_completed → returned-within-7-days. Activation = starts that create ≥ 1. TTV measured two ways: in-flow (start → create), and time-to-usable (start → published, plus edit-minutes in the following week) — because the rework should win on the second even if the review step costs a little on the first. Tag every event with the workflow variant + an anonymous session id so the two UI shapes can be compared as an A/B.

The insight

The telemetry the product roadmap needs and the telemetry the demo needs are the same stream — collected for free at the approval gate.

Where it landed A review_event log, an ImportRecord with a per-item decision trail, and a measurement section in the spec: funnel, two TTV definitions, A/B by variant.

09

Two workflow shapes to demo (A / B)

weekend 3

Refinement in the review step and refinement after content exists are the same job. That raised a bigger question: is the whole step-by-step wizard even the right shape?

PM · the thread that opened it

“Can’t we have a chat interface in the review step as well? The only difference in the review stage would be a card for each content created; when someone edits one content later, it’s just one content.”  …  “Or think of this being a full-page modal so we have more space.”

Align the primitives — one shared vocabulary of bounded steers and one event schema for both surfaces — but don’t force one layout. The content preview is what needs room; a chat sidebar wants ~350px; the activity cards ~260px. That doesn’t fit the current centred card.

PM · clarifying (after a question that missed)

“Not side by side — they’re two different ways. One is the current step 1–3 modal; I want to preserve it and demo it. Another is a 3-panel structure on a full-screen overlay.”  …  “Option 1, but with the 2nd and 3rd panels collapsed — they’re not needed in steps 1 and 2.”  …  “If I start with variant A, I’m OK finishing the whole process on it — don’t need to switch to B midway.”

Variant B: a full-screen overlay. Panel 1 (setup) is always there; panels 2 (output) and 3 (a chip-based refinement chat) stay collapsed until content exists. An A/B toggle in the app; both variants share all state underneath so the comparison stays honest. Skeleton first — layout and flow working, polish per panel afterward.

Claude askedDoes Variant B change only the review step, or more of the flow?
Review step onlyWhole flow reimagined
Chose “whole flow” — setup, output and refine on one canvas instead of three screens.
Claude askedThe refinement chat composer — chips only, or chips plus a free-text box?
Chips onlyChips + free text
Chose “chips only” — truest to “specific ways of refinement, not loose chat.”

Where it landed An A/B toggle. A = the step-by-step wizard (preserved). B = a full-screen 3-panel workspace — setup, output, chip-based refinement chat — panels revealing as the flow progresses.
